# S3 — Regressió de filtres i soft delete

## Immutable starting state

Use a pinned, disposable regression fixture revision whose test database contains active and soft-deleted records with matching `status` values. The fixture must declare the observed failing expectation and dataset hash before execution; it must not be generated by changing the shared application or by weakening a test. Start every repetition from a fresh clone/database.

## Controlled input

Provide the documented defect report: the `status` filter can include a record with non-null `deleted_at`. Ask the factory to diagnose the query, apply the minimum correction, and add regression coverage for status-only and combined filters. No permission, workflow, infrastructure, or production change is in scope.

## Terminal condition

The defect is reproduced against PostgreSQL, the query omission is identified, the minimal fix and regression tests are in one PR, and the complete applicable service validation passes. The run ends in a documented failure if reproduction or validation cannot be completed; no defect is introduced into the shared service.

## Expected evidence

Capture the immutable fixture/dataset identifier, reproduction request and response, query evidence, fix/test diff, full validation logs, PR/pipeline IDs, timestamps, and run record. Preserve the before/after evidence without fabricating an outcome.

## Human-intervention counting

Count distinct human clarifications, rerun approvals, or recovery actions. Planned observation and review are not interventions; manual edits outside the requested PR are prohibited.

## Cleanup and isolation

Use only a disposable clone, branch, database/schema, and workspace. Retain evidence, then clean disposable artifacts. Do not modify shared code, infrastructure, Proxmox, production, or mirror state.
